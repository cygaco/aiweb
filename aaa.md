Close the full compatibility-layer gap so the concierge picks restaurants by "who nearby actually delivers + actually has what I want + at a price we can quote" across pizzas, sides, and drinks. Today `checkItemAvailability` in `src/lib/compatibility.ts` only assesses pizza intent — sides and drinks go through the customization surface but never affect the `go` / `caution` / `no_go` verdict, so a Pepsi shop still ranks `go` when I asked for Coke and a place with one obscure side ranks `go` when I asked for wings. Five linked pieces. **First**, extend `checkItemAvailability` to accept an `intent_items` shape (pizza style + sides-by-name + drinks-by-name-and-brand-and-size) and return per-item states using the same evidence tiers the pizza path already uses — `menu_match` → `available` (high), `places_generic` template → `unknown` (low), `PIZZA_CUISINE_DEFAULTS` → explicitly ineligible-for-availability since display-only defaults can't grant evidence; combine into the existing assessment via a per-item map so the agent sees which items are confirmed vs which need in-call confirmation. **Second**, flip the entry flow on `start_pizza_order`: ask intent first ("what do you want?" — style, sides-by-name, drinks-by-name) and run discovery + compatibility *after* we know intent; rank restaurants by (delivers + covers address + has every requested item at known prices), with quality scoring instead of the current binary verdict — today the tool asks address first and tries to fit a single pizza intent, which breaks the moment intent has more than one dimension. **Third**, extend `menu-discovery.ts` to capture brand evidence from the website (Pepsi vs Coca-Cola portfolio, regional brands, store-brand water) so a Pepsi shop's drinks surface as real high-confidence Pepsi entries; defaults remain a true fallback only when real evidence is absent, never a substitute when real evidence exists. **Fourth**, harden the price-honesty wall: the agent must never quote, sum, or estimate a number not present in `menu.X.sizes[].price` with `menu_confidence: 'high'` — medium-confidence items remain priceless by design (the `DrinkOption` / `SideOption` type wall already enforces this for cart math, but pre-cart narration like "about $X total" still leaks estimates when menus are sparse; close that loop in the narration rule and in any pre-`prepare_order` total computation, so unknown prices show as "—" or "TBC on call" rather than as a synthesized average). **Fifth**, bring deals/promotions (`restaurant.menu.deals?`) under the same regime: a deal can be named only with verified savings math and only when its `components` match the actual cart shape; otherwise surface as "they have a deals page — I'll ask about specifics on the call." The whole change is the compatibility layer graduating from a pizza-only gate to the orchestrator of "real restaurant + real items + real prices" — extending the principle that already lives in `compatibility.ts` (pizza item-availability) to sides, drinks, brands, prices, and deals end-to-end, while keeping the narration honesty and type-wall guarantees the menu-honesty sprint just shipped.
